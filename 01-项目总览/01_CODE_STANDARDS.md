# 火锅食材 B2B 小程序与管理系统代码规范文档

> 适用范围：微信小程序客户端、网页客户端、网页管理端、公司官网宣传页、统一后端 API、CI/CD 与多环境部署。
>
> 文档目标：在公司规模较小、但未来会扩展到多个品牌、合作厂家、不同客户类型的前提下，建立一套可长期演进、可协作、可落地的企业级开发规范。

---

## 1. 项目目标

本项目面向 B2B 火锅食材业务，支持以下核心场景：

- 多品牌商品统一管理
- 餐饮门店、批发商等客户在线下单
- 合同价、客户专属价、人工调价
- 对公结算、月结、账期管理
- 库存、入库、出库、库存预警
- 销售、仓库、客服、管理员等角色协作
- 公司官网宣传获客
- 后续支持多个合作厂家接入平台

### 1.1 第一阶段交付范围

- 微信小程序客户端
- 网页客户端
- 网页管理端
- 公司官网宣传页
- 单体后端服务
- 基础 CI/CD

### 1.2 设计原则

- 先稳定，再扩展
- 先统一数据标准，再扩展业务差异
- 先单体架构，后模块拆分
- 先标准化接口、权限和日志，再做复杂自动化
- 所有业务都必须围绕“客户、商品、订单、库存、结算、权限、审计”六大核心对象展开

## 2. 推荐技术栈

### 2.1 前端

#### 微信小程序客户端
- 微信原生小程序
- JavaScript 或 TypeScript（建议后续统一 TypeScript）
- 组件化开发
- 统一请求封装、统一状态管理、统一授权处理

#### 网页客户端、管理端、官网
- Vue 3
- TypeScript
- Vite
- Pinia
- Vue Router
- Element Plus 用于管理端
- 官网宣传页可单独使用 Nuxt.js 或 Vue 3 SSR/SSG，也可先用同一套技术栈做静态官网

### 2.2 后端

- 单体服务优先
- RESTful API
- Node.js + NestJS，或 Java + Spring Boot，二选一
- 建议优先采用一套团队最熟悉的后端技术，不要为了“先进”而增加落地难度

### 2.3 数据与缓存

- MySQL：主业务库
- Redis：缓存、验证码、会话、分布式锁、热点数据
- 对象存储：商品图、合同、发票、资质文件、宣传图

### 2.4 CI/CD

- GitHub Actions
- 按环境区分：测试环境、生产环境
- 自动执行：安装依赖、校验、构建、测试、产物发布

## 3. 仓库与目录规范

建议采用单仓库、多应用目录结构：

```text
miniprogram/
├─ apps/
│  ├─ miniapp/                # 微信小程序
│  ├─ web-customer/           # 网页客户端
│  ├─ admin-web/              # 网页管理端
│  └─ official-site/          # 公司官网宣传页
├─ services/
│  └─ api/                    # 统一后端服务
├─ packages/
│  ├─ shared/                 # 共享工具、类型、常量
│  ├─ ui/                     # 共享 UI 组件
│  ├─ types/                  # 领域类型定义
│  └─ config/                 # 共享配置
├─ docs/
├─ scripts/
├─ .github/
│  └─ workflows/
└─ CODE_STANDARDS.md
```

### 3.1 目录设计原则

- 每个应用独立运行、独立构建、独立部署
- 共享代码只能放在 `packages/` 下
- 禁止业务应用之间直接互相引用私有文件
- 后端领域代码按业务模块拆分，不按技术层随意堆放

## 4. 命名规范

### 4.1 总体原则

- 统一使用英文命名
- 文件名、变量名、接口名要能表达业务含义
- 避免缩写，除非是行业通用缩写
- 业务术语必须统一，例如：
  - 客户：customer
  - 品牌：brand
  - 商品：product
  - SKU：sku
  - 订单：order
  - 库存：inventory
  - 仓库：warehouse
  - 账期：creditTerm
  - 对公结算：corporateBilling

### 4.2 文件命名

- 组件：`PascalCase`
- 工具函数：`camelCase`
- 页面目录：`kebab-case` 或业务英文名
- 类型定义：`*.types.ts`
- 常量：`*.constants.ts`
- API：`*.api.ts`
- 服务层：`*.service.ts`
- 校验规则：`*.schema.ts`

### 4.3 变量命名

- 布尔值必须能读出真假语义
  - `isActive`
  - `hasInventory`
  - `canApprove`
- 集合使用复数形式
  - `customers`
  - `orders`
  - `products`
- 避免无意义命名
  - 不要用 `data1`、`temp`、`list2`

### 4.4 接口命名

- RESTful 路径使用复数名词
  - `/api/customers`
  - `/api/orders`
  - `/api/inventories`
- 动作性操作使用语义化子路径
  - `/api/orders/{id}/confirm`
  - `/api/orders/{id}/cancel`
  - `/api/orders/{id}/approve`

## 5. 前端代码规范

## 5.1 通用要求

- 所有页面、组件、服务层必须拆分职责
- 页面只负责组合，不直接写复杂业务逻辑
- 业务逻辑放在 `service`、`store` 或 `composable` 中
- 请求必须通过统一封装层，不允许页面内直接散写 `fetch` 或 `wx.request`

### 5.2 页面结构

每个页面建议包含：

- 页面入口
- 页面状态
- 页面事件处理
- 页面渲染
- 页面私有样式

### 5.3 组件规范

- 一个组件只做一类事情
- 可复用的业务块必须组件化
- 管理端表格、筛选、弹窗、表单必须拆分为独立组件
- 小程序端卡片、商品项、订单项、标签组件单独沉淀

### 5.4 状态管理

- 仅全局共享的数据进入 store
- 例如：
  - 登录状态
  - 当前租户/品牌
  - 当前用户权限
  - 购物车或下单草稿
  - 站点配置
- 页面局部状态不要放进全局 store

### 5.5 样式规范

- 优先使用设计系统变量
- 不要在页面中硬编码大量颜色值和间距值
- 建立统一的颜色、字号、圆角、阴影、间距变量
- 官网和对外页面风格建议遵循“极简、高级、克制、可信赖”原则

### 5.6 前端异常处理

- 所有接口错误都要统一提示
- 不允许静默失败
- 登录失效必须统一跳转登录
- 权限不足必须明确提示

## 6. 后端代码规范

### 6.1 分层原则

建议后端至少分为以下层：

- Controller / Route：接收请求、返回响应
- Service：承载业务逻辑
- Repository / DAO：数据访问
- Domain：核心领域对象与规则
- DTO / VO：输入输出对象
- Middleware / Guard：鉴权、审计、限流

### 6.2 模块划分

建议按业务模块拆分：

- auth：登录、权限、验证码
- tenant：租户、品牌、组织
- customer：客户档案、客户等级、专属价格
- product：商品、SKU、单位、分类
- order：订单、订单明细、状态流转
- inventory：库存、入库、出库、预警
- billing：结算、账期、对公信息
- delivery：配送状态、送达记录
- audit：操作日志、审计记录
- file：文件上传、图片、资质材料
- system：系统配置、参数、字典

### 6.3 业务规则必须落库

以下规则不能只写在前端：

- 客户等级
- 专属价格
- 手动调价记录
- 订单状态流转
- 库存扣减规则
- 权限判断
- 审计日志

### 6.4 事务规范

- 订单创建、库存扣减、价格确认、日志写入必须保证事务一致性
- 需要多个表联动的业务必须使用事务
- 失败必须可回滚

### 6.5 错误码规范

统一错误码格式：

- `AUTH_`：认证与授权
- `CUS_`：客户相关
- `PRO_`：商品相关
- `ORD_`：订单相关
- `INV_`：库存相关
- `PAY_`：支付/结算相关
- `SYS_`：系统错误

示例：
- `ORD_1001` 订单不存在
- `INV_2002` 库存不足
- `AUTH_3001` 登录失效

## 7. 数据库规范

### 7.1 命名规则

- 数据库名：业务英文小写，如 `miniprogram_b2b`
- 表名：复数、下划线风格，如 `customers`, `orders`, `order_items`
- 字段名：小写下划线
- 主键统一：`id`
- 外键统一：`xxx_id`

### 7.2 核心表建议

- `tenants`
- `brands`
- `users`
- `roles`
- `permissions`
- `customers`
- `customer_price_rules`
- `products`
- `product_skus`
- `inventories`
- `inventory_logs`
- `orders`
- `order_items`
- `settlements`
- `delivery_records`
- `audit_logs`
- `files`

### 7.3 字段规范

建议统一字段：

- `created_at`
- `updated_at`
- `deleted_at`
- `created_by`
- `updated_by`
- `tenant_id`
- `brand_id`
- `status`

### 7.4 多租户规范

项目必须预留多租户能力：

- 所有核心业务表默认带 `tenant_id`
- 如果一个品牌和一个租户强绑定，也建议保留 `brand_id`
- 所有查询必须带租户过滤
- 超级管理员可以跨租户查看，但必须审计记录

## 8. 权限与角色规范

### 8.1 角色模型

系统至少支持：

- 超级管理员
- 管理员
- 销售
- 仓库
- 客服
- 财务

### 8.2 权限粒度

权限至少分三层：

- 菜单权限
- 页面权限
- 按钮/操作权限

### 8.3 权限分配原则

- 超级管理员拥有所有权限
- 其他角色只能分配其职责范围内权限
- 财务不能改库存核心数据，仓库不能改结算数据，销售不能随意改审计记录

### 8.4 审计要求

以下操作必须留痕：

- 登录/退出
- 订单创建、修改、取消
- 手动改价
- 库存调整
- 权限变更
- 角色变更
- 结算单修改

---

## 9. 订单与价格规范

### 9.1 价格规则

当前业务支持：

- 基础售价
- 客户等级价
- 合同价
- 专供客户人工调价

### 9.2 价格优先级

建议优先级如下：

1. 手动调价
2. 客户专属协议价
3. 客户等级价
4. 基础售价

### 9.3 订单状态建议

- `draft` 草稿
- `pending_confirm` 待确认
- `confirmed` 已确认
- `picking` 拣货中
- `delivering` 配送中
- `completed` 已完成
- `cancelled` 已取消
- `refunded` 已退款/冲销

### 9.4 订单修改原则

- 已确认订单不可直接覆盖修改
- 修改必须产生变更记录
- 关键字段修改需要审批或二次确认

---

## 10. 库存规范

### 10.1 库存策略

第一期采用基础库存管理：

- 入库
- 出库
- 调拨预留
- 库存预警

### 10.2 库存变动原则

- 所有库存变化必须写入日志
- 库存不能出现负数，除非业务明确允许欠货
- 下单和出库需要区分“预占”和“实扣”

### 10.3 预警规则

- 低库存预警
- 超卖预警
- 临期预警可作为第二阶段扩展

---

## 11. 接口规范

### 11.1 RESTful 规则

- GET 查询
- POST 新增/动作
- PUT 全量更新
- PATCH 局部更新
- DELETE 删除

### 11.2 响应格式

统一响应结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "requestId": "xxx"
}
```

### 11.3 分页规范

统一分页参数：

- `page`
- `pageSize`
- `total`
- `items`

### 11.4 接口版本

- API 必须带版本前缀，如 `/api/v1`
- 重大变更通过新版本兼容，不直接破坏旧接口

## 12. 登录与认证规范

### 12.1 登录方式

- 手机号 + 验证码登录
- 后续可扩展微信授权绑定

### 12.2 Token 规范

- Access Token + Refresh Token
- Access Token 有效期较短
- Refresh Token 轮换机制

### 12.3 安全要求

- 验证码限流
- 登录失败次数限制
- 敏感接口鉴权
- 管理端强制二次校验可后续增加

### 13.1 日志分级

- `info`

### 13.2 必须记录的内容

### 13.3 审计日志字段

- 操作人

- 操作类型
- 目标对象
- 操作前数据
- 操作后数据
- 时间
- IP
- 设备信息

## 14. 测试规范

### 14.1 必须覆盖的测试

- 核心业务单元测试
- 权限测试
- 订单状态流转测试
- 库存扣减测试
- 价格计算测试

### 14.2 测试要求

- 新增核心业务逻辑必须附带测试
- 提交前不能有明显失败的测试
- CI 中必须运行 lint + test + build

## 15. 提交与分支规范

### 15.1 分支命名

- `main`：生产分支
- `develop`：集成分支
- `feature/xxx`：功能分支
- `fix/xxx`：修复分支
- `release/xxx`：发布分支

### 15.2 提交信息规范

建议采用 Conventional Commits：

- `feat:` 新功能
- `fix:` 修复
- `refactor:` 重构
- `docs:` 文档
- `test:` 测试
- `chore:` 工程化

示例：

- `feat(order): add customer price confirmation flow`
- `fix(inventory): prevent negative stock on checkout`
- `docs: add enterprise coding standards`

### 15.3 代码评审原则

- 所有合并必须经过至少一次评审
- 核心业务模块必须重点审查权限、事务、日志
- 不允许带着明显 TODO 进入生产分支

---

## 16. CI/CD 规范

### 16.1 基本流水线

每次提交应至少执行：

1. 安装依赖
2. 代码格式检查
3. 静态检查
4. 单元测试
5. 构建产物
6. 预发布部署或生产部署

### 16.2 环境划分

- 测试环境：自动部署
- 生产环境：人工确认后部署

### 16.3 发布原则

- 前端与后端独立构建
- 小程序需要专门发布流程
- 官网、客户 Web、管理端可分别部署
- 失败自动回滚机制建议第二阶段补齐

---

## 17. 安全规范

- 所有输入必须校验
- 文件上传必须限制类型和大小
- 敏感信息不能写入前端代码
- 生产环境禁止打印密钥
- 管理端必须最小权限原则
- 多租户数据必须强隔离

---

## 18. 性能规范

- 列表必须分页
- 大查询必须加索引
- 高频配置项使用缓存
- 图片走 CDN 或对象存储
- 避免在前端做超大数据计算

---

## 19. 页面与视觉规范

整体视觉风格建议：

- 极简
- 高级
- 克制
- 可信赖
- 偏 B2B 工业感

建议风格关键词：

- 留白充足
- 深浅对比明确
- 强调信息层级
- 不要过度装饰
- 交互反馈清晰但不过度花哨

### 19.1 官网宣传页重点

- 品牌背书
- 产品能力
- 客户案例
- 服务流程
- 联系方式
- 留资表单

## 22. 文档维护规则

- 本文档是项目规范的最高优先级之一
- 新功能上线前必须先补充相关规范
- 代码实现不得违反本文档约束

## 23. 结论

本项目不是简单的小程序，而是一个面向多品牌、多客户、多角色协同的 B2B 食材销售与管理平台。

因此，代码规范必须满足三个目标：

1. 能快速上线
2. 能稳定运营
3. 能支撑后续扩展

后续所有前端、后端、数据库、部署与测试规范，都应围绕这份标准展开。
