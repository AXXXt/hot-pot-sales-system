# 全局商品分类与商品状态开关布局设计

日期：2026-07-29  
状态：已实施；本次相关验证通过，全量后端测试存在 1 项仪表盘趋势断言失败

## 1. 背景

管理端分类管理当前要求每个分类绑定一个品牌，分类列表也展示品牌。商品编辑页的五个状态开关采用不一致的列宽，形成三项一行、两项一行但间距和起始位置不统一的视觉效果。

本次按已确认的方案三实施：商品分类改为租户内共享的全局分类，不再与品牌建立直接或间接的筛选关系；商品本身继续保留品牌字段。商品状态开关采用三列分组布局，第二行两项左对齐。

## 2. 目标

- 删除分类管理中的品牌列和品牌选择功能。
- 删除 `ProductCategory` 与 `Brand` 的数据库关联及 `brandId` 字段。
- 分类查询接口不再接收或使用品牌参数。
- 管理端和小程序统一获取全局分类列表。
- 商品、客户等级、价格规则和订单中的品牌关系保持不变。
- 商品编辑页五个状态开关按三列等宽排列，第二行两项左对齐。
- 窄屏下开关布局自动降为单列。

## 3. 非目标

- 不删除品牌管理功能。
- 不删除商品、客户、价格规则或订单上的品牌字段。
- 不修改商品列表的品牌筛选和商品品牌展示。
- 不合并、重命名或自动删除现有分类。
- 不改变分类父子层级、排序、状态和商品归类逻辑。
- 不调整商品编辑页其他字段、主图上传或 SKU 管理。

## 4. 方案选择

采用“分类完全全局化”的方案：

- 分类记录仅属于租户，不属于品牌。
- 分类接口始终返回当前用户可见商品涉及的全局分类，不根据品牌过滤。
- 小程序切换品牌时商品列表仍按商品品牌过滤，但分类导航保持全局一致。

不采用仅删除管理端控件的方案，因为数据库仍会强制分类绑定品牌。也不采用通过商品品牌动态反查分类的方案，因为该方案仍会让分类导航随品牌变化，不符合已确认的完全全局化要求。

## 5. 数据模型设计

### 5.1 ProductCategory

从 `ProductCategory` 删除：

- `brandId` 字段及 `brand_id` 数据库列。
- `brand` 关系。
- `@@unique([tenantId, brandId, code])`。
- `@@index([tenantId, brandId, status])`。

调整为：

- 分类编码在租户内唯一：`@@unique([tenantId, code])`。
- 分类状态查询使用：`@@index([tenantId, status])`。

### 5.2 Brand

从 `Brand` 删除 `categories ProductCategory[]` 反向关系。品牌与商品、用户访问权限、客户等级、价格规则和订单的现有关系不变。

### 5.3 数据迁移

新增 Prisma 迁移：

1. 检查同一租户下是否存在跨品牌重复的分类 `code`。
2. 若存在重复编码，迁移应失败并明确提示，避免静默合并或覆盖分类。
3. 删除分类到品牌的外键。
4. 删除旧的品牌组合唯一索引和查询索引。
5. 删除 `brand_id` 列。
6. 新增租户与分类编码唯一索引。
7. 新增租户与状态查询索引。

现有商品通过 `category_id` 关联分类，删除分类品牌字段不会改变商品的分类引用。

## 6. 后端接口设计

### 6.1 分类查询

`GET /api/v1/product-categories`：

- 删除 `brandId` 查询参数及 Swagger 描述。
- 服务层删除 `brandId` 入参和 `where.brandId` 条件。
- 保留分类状态、排序和商品可见性过滤。
- 返回所有包含当前用户可见商品的全局分类。

### 6.2 分类创建与更新

- `CreateCategoryDto` 删除必填 `brandId`。
- `UpdateCategoryDto` 删除可选 `brandId`。
- 创建分类时只写入 `tenantId`、`code`、`name`、`sortOrder` 和 `parentId`。
- 编辑分类继续只允许更新名称、编码、父级、排序等分类自身字段。

### 6.3 开发种子数据

- 分类 upsert 唯一键从 `tenantId_brandId_code` 改为 `tenantId_code`。
- 分类创建数据不再写入 `brandId`。
- 商品种子数据仍写入自己的 `brandId` 和 `categoryId`。

## 7. 管理端设计

### 7.1 分类管理

`CategoryView.vue` 删除：

- `getBrands` 导入和品牌列表状态。
- 加载分类时的品牌接口请求。
- 分类表格中的“品牌”列。
- 分类表单中的品牌下拉框。
- 表单状态中的 `brandId`。
- 创建分类请求中的 `brandId`。
- 保存按钮对 `brandId` 的必填校验。

分类弹窗保留名称、父级分类和排序，其他交互不变。

### 7.2 分类 API

管理端 `getCategories()` 不再接收 `brandId`，请求中不再发送品牌参数。

### 7.3 商品状态开关

将五个状态开关放入独立的响应式网格：

- 桌面端固定三列等宽。
- 第一行：工厂自产、支持样品、推荐商品。
- 第二行：新品、热销，左对齐占据前两列。
- 各项标签、开关起始位置、行列间距保持一致。
- 小屏幕降为单列，避免标签和开关拥挤。

开关字段、提交参数和业务含义不变，仅调整模板结构和布局样式。

## 8. 小程序设计

- `getProductCategories()` 不再接收分类品牌参数。
- 分类页加载分类时不再传入当前品牌 ID。
- 商品列表请求继续传入当前品牌 ID，因此切换品牌仍只展示该品牌商品。
- 全局分类中没有当前品牌商品的分类被选中时，商品列表允许显示为空；这是方案三的预期行为。

## 9. 测试设计

### 9.1 后端

- 分类接口在不传 `brandId` 时正常返回。
- 分类接口不再向服务层传递品牌 ID。
- 分类服务查询条件不包含 `brandId`。
- 分类服务仍应用状态、排序和用户商品可见性条件。
- 创建分类不需要 `brandId`。
- Prisma schema 校验和客户端生成通过。
- 迁移在无重复分类编码的数据上成功。

### 9.2 管理端

- 分类页面源码不再引用 `getBrands`、`brands` 或 `form.brandId`。
- 分类表格和弹窗不再出现“品牌”。
- 只填写分类名称即可启用保存按钮。
- 商品状态开关按三列网格渲染，并具备窄屏单列规则。
- 管理端 TypeScript 检查、单元测试和生产构建通过。

### 9.3 小程序

- 分类请求不再携带 `brandId`。
- 分类页面仍能加载并切换分类。
- 商品列表仍按当前品牌请求商品。
- 现有小程序测试通过。

## 10. 验收标准

- 分类管理页面完全不显示品牌列或品牌选择控件。
- 新建和编辑分类不需要品牌即可成功保存。
- 数据库分类表不再包含 `brand_id`，Prisma 不再声明分类品牌关系。
- 分类接口和前端分类请求不再接收或发送品牌参数。
- 商品及其他业务对象的品牌功能不受影响。
- 商品编辑页状态开关采用三列加两列左对齐的有序布局。
- 后端测试、管理端测试与构建、小程序测试和 Prisma 校验全部通过。
