# 火锅食材 B2B 小程序与管理系统项目技术架构设计文档

> 适用范围：微信小程序客户端、网页客户端、网页管理端、公司官网宣传页、统一后端服务、数据库、缓存、对象存储、CI/CD、监控与部署。
>
> 文档目标：在当前公司规模不大、但业务会持续扩展到多品牌、多客户、多合作厂家、多角色协同的情况下，设计一套可以真实落地、可持续演进、可维护、可部署的技术架构。

---

## 1. 项目背景

本项目是一个面向 B2B 火锅食材销售的数字化平台，服务对象包括：

- 餐饮门店
- 连锁餐饮
- 批发商
- 合作厂家
- 内部销售、仓库、客服、管理员

业务范围覆盖：

- 商品展示与下单
- 客户专属价格体系
- 订单确认与履约
- 库存管理
- 基础结算与账期管理
- 多角色权限控制
- 操作审计
- 公司官网宣传获客

本系统不是单纯的小程序，而是一个“前台获客 + 客户下单 + 后台运营 + 组织协同 + 未来扩展”的完整业务平台。

## 3. 总体架构方案

建议采用“单体后端 + 多前端应用 + 共享基础设施”的架构。

### 3.1 架构原则

- 前端按场景拆分，后端统一承载
- 后端优先单体，不做过早微服务拆分
- 领域模块化，代码组织上按业务域拆分
- 所有系统共享统一用户体系、租户体系、权限体系、审计体系

### 3.2 系统组成

- 微信小程序客户端：客户移动端下单入口
- 网页客户端：适合 PC 浏览和复购操作
- 网页管理端：销售、仓库、客服、管理员日常运营
- 官网宣传页：品牌展示、获客、留资
- 后端 API 服务：统一业务中枢
- MySQL：业务主数据
- Redis：缓存、验证码、会话、锁
- 对象存储：商品图、合同、资质、发票
- CI/CD：自动化构建和部署

### 3.3 推荐部署拓扑

```text
用户浏览器 / 微信小程序
        │
        ▼
   CDN / 静态资源
        │
        ▼
   Nginx / API Gateway
        │
        ▼
   统一后端服务（单体）
     ├─ auth
     ├─ tenant
     ├─ customer
     ├─ product
     ├─ order
     ├─ inventory
     ├─ billing
     ├─ audit
     ├─ file
     └─ system
        │
        ├── MySQL
        ├── Redis
        └── Object Storage
```

## 4. 技术选型

### 4.1 前端选型

#### 4.1.1 微信小程序

- 原生微信小程序
- JavaScript 起步，后续逐步 TypeScript 化
- 适合业务页面快速开发

#### 4.1.2 网页客户端 / 管理端 / 官网

- Vue 3
- TypeScript
- Vite
- Pinia
- Vue Router
- Element Plus 用于管理端

### 4.2 后端选型

推荐两种方案二选一：

- Node.js + NestJS
- Java + Spring Boot

结合当前项目规模和团队可维护性，建议优先选“团队最熟悉的栈”。如果团队偏前端协作，NestJS 更容易统一 TypeScript 体验；如果团队偏传统企业系统，Spring Boot 更稳妥。

### 4.3 数据与基础设施

- MySQL：订单、客户、商品、库存、权限、审计等核心数据
- Redis：验证码、Token 辅助、热点缓存、分布式锁、限流
- 对象存储：图片、附件、合同、资质、导出文件
- Nginx：静态资源与反向代理
- GitHub Actions：CI/CD 流水线

## 5. 前端架构设计

### 5.1 应用拆分

建议前端拆为 4 个独立应用：

- `miniapp`：微信小程序
- `web-customer`：网页客户下单端
- `admin-web`：管理端
- `official-site`：官网宣传页

### 5.2 前端代码组织原则

- 页面只负责展示与编排
- 业务逻辑下沉到 `service`、`store`、`composable`
- API 请求统一封装
- 全局状态只放跨页面共享数据
- 样式统一走设计系统变量

### 5.3 前端模块职责

#### 微信小程序

- 首页
- 商品分类
- 商品详情
- 客户下单
- 订单列表
- 订单详情
- 个人中心
- 登录与授权

#### 网页客户端

- 商品浏览
- 快速复购
- 下单
- 订单查询
- 对账查看
- 客户资料查看

#### 管理端

- 客户管理
- 品牌管理
- 商品管理
- 库存管理
- 订单管理
- 价格管理
- 角色权限管理
- 审计日志
- 基础配置

#### 官网

- 品牌介绍
- 产品能力展示
- 服务流程
- 合作案例
- 联系方式
- 留资表单

### 5.4 前端状态管理

推荐分类管理：

- 用户登录状态
- 当前租户/品牌
- 权限集合
- 商品筛选条件
- 购物车/下单草稿
- 系统配置

避免将列表分页数据、临时弹窗状态、页面局部表单状态放入全局 store。

### 5.5 UI 与设计约束

整体视觉建议遵循：

- 极简
- 高级
- 克制
- 工业可信赖感

对管理端采用高密度信息布局，对官网和客户端采用更强留白和更简洁的信息层级。

## 6. 后端架构设计

### 6.1 架构形式

采用模块化单体：

- 一个后端部署单元
- 内部按业务域拆分模块
- 共享认证、权限、日志、文件、字典等能力

这种方式适合当前阶段，原因是：

- 开发效率高
- 部署简单
- 运维成本低
- 后续可拆分

### 6.2 后端分层

建议使用以下分层：

- API 层：接收请求、参数校验、响应包装
- Application 层：编排业务流程
- Domain 层：核心业务规则
- Infrastructure 层：数据库、缓存、文件、外部服务

如果使用 NestJS，也可以映射为：

- Controller
- Service
- Repository
- Module
- Guard / Interceptor / Pipe

### 6.3 核心模块划分

#### customer

- 客户档案

- 客户专属价格
- 账期配置

#### product

- 商品管理
- SKU 管理
- 分类管理
- 单位管理

#### order

- 下单
- 改价
- 确认订单
- 订单流转
- 订单明细

#### inventory

- 入库

#### billing

#### delivery

## 7. 数据架构设计

### 7.1 数据库设计原则

- 所有核心业务表带 `tenant_id`
- 关键表保留 `brand_id`
- 软删除优先
- 关键操作记录历史数据
- 状态字段统一枚举化
- 不允许前端决定核心业务状态

### 7.2 核心实体关系

- 租户 `tenant` 拥有多个品牌 `brand`
- 品牌下有多个客户 `customer`
- 客户可以有多个价格规则 `customer_price_rule`
- 商品 `product` 下有多个 SKU `product_sku`
- 订单 `order` 下有多个订单项 `order_item`
- 订单会影响库存 `inventory` 和库存日志 `inventory_log`
- 所有关键操作写入 `audit_log`

### 7.3 建议核心表

- `tenants`
- `brands`
- `users`
- `roles`
- `permissions`
- `user_roles`
- `role_permissions`
- `customers`
- `customer_price_rules`
- `customer_accounts`
- `products`
- `product_skus`
- `product_categories`
- `inventories`
- `inventory_logs`
- `orders`
- `order_items`
- `order_price_adjustments`
- `settlements`
- `delivery_records`
- `audit_logs`
- `files`
- `system_configs`

### 7.4 多租户策略

当前建议采用“字段隔离型多租户”：

- 所有业务表通过 `tenant_id` 区分租户
- 所有查询默认自动注入租户过滤
- 超级管理员可跨租户查看，但所有行为必须审计
- 未来如果租户规模非常大，再考虑库级隔离

这个方案适合当前阶段，因为它实现简单、成本低、可维护性强。

## 8. 权限架构设计

### 8.1 角色模型

建议默认角色：

- 超级管理员
- 管理员
- 销售
- 仓库
- 客服
- 财务

### 8.2 权限模型

权限分为三层：

- 菜单权限
- 页面权限
- 按钮/接口权限

### 8.3 鉴权流程

1. 用户手机号验证码登录
2. 后端签发 token
3. 前端保存 token
4. 请求携带 token
5. 后端校验身份、租户、角色和权限
6. 通过审计中间件记录敏感操作

### 8.4 权限边界

- 超级管理员可管理所有租户和品牌
- 销售只能操作自己负责的客户和订单范围
- 仓库只能处理库存和拣货相关操作
- 财务只能看结算和对账相关数据
- 客服主要处理咨询、售后、订单协助

## 9. 业务流程架构

### 9.1 客户下单流程

1. 客户登录
2. 选择品牌 / 商品
3. 查看价格
4. 添加到购物车
5. 提交订单
6. 系统校验价格和库存
7. 订单进入待确认或直接确认状态
8. 仓库开始履约
9. 订单完成并进入结算记录

### 9.2 价格计算流程

建议价格优先级：

1. 人工调价
2. 客户专属协议价
3. 客户等级价
4. 基础售价

### 9.3 库存处理流程

- 订单提交时进行库存校验
- 需要时进行预占
- 仓库出库时进行实扣
- 所有变动写库存日志

### 9.4 审计流程

- 所有敏感动作写入审计日志
- 至少记录：操作者、对象、前值、后值、时间、IP、来源端

## 10. 接口架构设计

### 10.1 API 风格

统一采用 RESTful：

- `GET /api/v1/customers`
- `POST /api/v1/orders`
- `PATCH /api/v1/orders/{id}`
- `POST /api/v1/orders/{id}/confirm`

### 10.2 接口统一规范

- 统一响应结构
- 统一分页结构
- 统一错误码体系
- 统一日志请求 ID
- 统一版本前缀 `/api/v1`

### 10.3 接口分层

- 公共接口：登录、验证码、基础配置
- 客户端接口：商品、下单、订单查询
- 管理端接口：商品、客户、库存、权限、审计、配置

## 11. 安全架构设计

### 11.1 认证安全

- 手机号验证码限流
- Token 过期控制
- Refresh Token 轮换
- 敏感接口强校验

### 11.2 数据安全

- 敏感数据脱敏
- 上传文件类型白名单
- 密钥只存服务端环境变量
- 生产环境禁止输出敏感日志

### 11.3 多租户安全

- 查询层强制 tenant 过滤
- 后端统一拦截跨租户访问
- 超级管理员操作必须审计

## 13. 部署架构设计

### 13.1 推荐部署方式

- 前端静态资源：CDN / 对象存储 / 静态站点
- 后端服务：Docker 容器部署
- 数据库：独立主机或托管服务
- Redis：独立实例
- 文件存储：对象存储

### 13.2 初期部署建议

对于当前阶段，建议：

- 1 套测试环境
- 1 套生产环境
- 后端单实例起步
- 数据库定时备份
- 日志集中存储

### 13.3 可扩展性预留

未来如果访问量增长，可以平滑扩展：

- 后端多实例水平扩容
- Redis 高可用
- 数据库读写分离
- 静态资源 CDN 化
- 按模块拆分服务

## 17. 风险与规避

### 17.1 业务风险

- 品牌、厂家、客户关系复杂
- 价格规则容易变动
- 多角色权限容易失控

规避方式：

- 统一租户与品牌模型
- 价格规则落库
- 权限与审计标准化

### 17.2 技术风险

- 早期架构过重
- 前端应用过多导致维护复杂
- 未统一接口规范导致后期难改

规避方式：

- 单体后端
- 模块化拆分
- 强制 API 版本
- 统一前端基础库

## 18. 结论

这套架构的核心不是“炫技”，而是“能活下来并持续增长”。

对于当前这类 B2B 火锅食材业务，最优解不是一开始就上复杂微服务，而是：

- 前端按场景拆分
- 后端模块化单体
- 数据统一建模
- 权限和审计前置
- CI/CD 标准化
- 为多品牌、多厂家、多租户预留扩展

如果后续业务规模增长，这套架构可以逐步演进，而不会推倒重来。
