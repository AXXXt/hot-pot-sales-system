# 火锅食材 B2B 项目国内可落地 CI/CD 架构方案

> 适用范围：微信小程序客户端、网页客户端、网页管理端、公司官网宣传页、统一后端 API。
>
> 目标：在国内网络环境下，提供一套稳定、可维护、可审计、适合真实商业项目的 CI/CD 方案，兼顾当前团队规模与后续业务扩展。

---

## 1. 设计目标

本项目的 CI/CD 体系需要同时满足以下要求：

- 国内网络环境下可稳定执行
- 构建、测试、部署流程标准化
- 支持测试环境与生产环境分离
- 支持前端多应用分别发布
- 支持小程序专项发布流程
- 支持人工审批后再上线生产
- 支持失败可追踪、可回滚、可审计
- 支持未来迁移到更大规模团队协作

---

## 2. 核心结论

对于这个项目，最推荐的落地策略不是“全量依赖 GitHub Actions 直连部署”，而是采用 **混合式 CI/CD 架构**：

- **GitHub 负责代码仓库与基础 CI 校验**
- **国内云环境负责测试/生产部署**
- **构建产物通过制品库或对象存储传递**
- **微信小程序单独走上传与审核流程**

这样能最大限度减少国内网络波动对交付的影响。

---

## 3. 推荐架构总览

```text
开发者提交代码
      │
      ▼
GitHub 仓库
      │
      ├── GitHub Actions：Lint / Test / Build
      │
      ├── 生成前端静态产物 / 后端镜像 / 小程序待发布包
      │
      ▼
国内制品存储 / 对象存储 / 容器仓库
      │
      ├── 测试环境自动部署
      ├── 生产环境人工确认后部署
      └── 小程序上传到微信平台
```

---

## 4. 为什么要采用混合式方案

### 4.1 GitHub Actions 的优势

- 代码评审和自动检查方便
- 与 GitHub 仓库天然集成
- 可复用大量公开 action
- 适合做基础质量门禁

### 4.2 国内可落地的必要性

国内真实项目中常见问题包括：

- GitHub 访问不稳定
- npm/pnpm 拉依赖慢
- 部署服务器在国内，跨境 SSH 不稳定
- 小程序上传、审核需要更细粒度的发布控制

所以建议把“构建”和“部署”适度拆开，避免所有环节都绑死在 GitHub 上。

---

## 5. 推荐落地方案

### 方案 A：GitHub Actions + 国内云服务器部署 + 制品传递

这是最推荐的方案，适合当前项目。

#### 流程

1. 开发者提交代码到 GitHub
2. GitHub Actions 执行：
   - 安装依赖
   - 代码格式化检查
   - Lint
   - 单元测试
   - 构建前端产物和后端产物
3. 产物上传到：
   - 阿里云 OSS / 腾讯云 COS / 华为云 OBS
   - 或者国内 Docker Registry
4. 国内测试服务器自动拉取并部署
5. 生产环境由人工确认后部署
6. 微信小程序产物单独上传到微信平台审核

#### 适用场景

- 团队规模较小
- 想尽快落地
- 希望保留 GitHub 协作体验
- 生产环境部署在国内云服务器

---

### 方案 B：国内 DevOps 平台做完整 CI/CD

可选平台：

- 腾讯云 CODING
- 阿里云 DevOps
- 华为云 DevCloud
- Gitee CI/CD

#### 优点

- 国内访问稳定
- 更适合企业内部审批流
- 一体化部署更省心

#### 缺点

- 需要迁移仓库或做双平台同步
- 公开 action 生态不如 GitHub 丰富
- 一些国际化工具链接入成本略高

#### 适用场景

- 团队明确长期在国内平台运维
- 对稳定性要求高于生态便利性
- 未来会有更多运维与发布协作人员

---

### 方案 C：GitHub Actions 只做校验，部署完全本地化

#### 流程

1. GitHub Actions 只做 lint/test/build
2. 产物上传到制品库
3. 国内部署机器通过定时任务或 webhook 拉取产物
4. 管理员在国内平台进行发布确认

#### 优点

- GitHub 只承担轻量任务
- 部署链路更稳
- 易于审计

#### 缺点

- 初期配置稍复杂
- 运维脚本需要标准化

---

## 6. 最终推荐方案

对于本项目，建议采用以下组合：

### 6.1 推荐组合

- **代码仓库**：GitHub
- **CI 校验**：GitHub Actions
- **前端构建产物**：上传到国内 OSS/COS/OBS
- **后端部署**：国内服务器 Docker 部署
- **小程序发布**：独立上传流程
- **生产发布**：人工审批后执行

### 6.2 推荐原因

- 兼顾 GitHub 协作便利性
- 降低国内网络不稳定带来的风险
- 便于以后切换到国内 DevOps 平台
- 适合当前公司规模和商业落地节奏

---

## 7. 环境划分

建议至少划分两个环境：

### 7.1 测试环境

用途：

- 日常联调
- 提测验证
- QA 验收
- 管理端功能验证

特征：

- 自动部署
- 数据可重置
- 日志完整
- 不对外开放或仅限制访问

### 7.2 生产环境

用途：

- 正式客户使用
- 对外官网展示
- 小程序正式访问

特征：

- 手动确认后发布
- 配置受控
- 数据必须备份
- 支持回滚

---

## 8. 各端部署方案

## 8.1 微信小程序

### 发布流程

1. 开发完成后构建小程序代码
2. 生成待上传版本
3. 使用微信开发者工具或自动化脚本上传
4. 由产品/负责人进行版本审核
5. 审核通过后发布

### 建议策略

- 测试环境小程序和正式小程序分开
- 提前建立“测试版”与“正式版”的区分
- 发布前必须完成接口联调和回归测试

### 注意事项

- 小程序发布不建议完全依赖“无人值守”自动上线
- 需要人工审批控制版本质量

---

## 8.2 网页客户端

### 部署方式

- 构建静态资源
- 上传到对象存储或静态站点
- 通过 CDN 分发

### 推荐流程

- 提交代码触发 CI
- 构建完成后上传测试环境
- 合并到主分支后人工确认上线生产环境

---

## 8.3 网页管理端

### 部署方式

- 与网页客户端类似，使用静态站点部署
- 若权限较复杂，可通过 Nginx 代理到前端静态资源

### 推荐流程

- 测试环境自动部署
- 生产环境人工确认
- 生产发布后强制刷新缓存

---

## 8.4 公司官网宣传页

### 部署方式

- 优先静态化
- CDN + 对象存储 + 缓存策略
- 如有 SEO 需求，可考虑 SSR/SSG

### 推荐流程

- 变更频率较低，可与前端主仓库分开部署
- 发布流程尽量简单稳定

---

## 8.5 后端服务

### 部署方式

- Docker 容器部署
- 国内云服务器运行
- 通过 Nginx 或网关反向代理

### 推荐流程

1. GitHub Actions 构建后端镜像
2. 推送到国内镜像仓库
3. 测试环境自动拉取最新镜像并重启
4. 生产环境需要人工确认后切换镜像版本

### 推荐实践

- 镜像版本必须带 Git 提交号或语义版本
- 不使用 `latest` 作为生产唯一版本标识
- 数据库迁移必须独立于应用部署执行

---

## 9. 构建与制品策略

### 9.1 前端制品

前端构建后输出：

- 静态 HTML/CSS/JS
- 静态资源图片
- source map 可选择是否上传到私有存储

### 9.2 后端制品

后端构建后输出：

- Docker 镜像
- 或可执行包
- 数据库迁移脚本

### 9.3 小程序制品

- 小程序构建产物
- 上传包
- 审核发布记录

### 9.4 制品存放位置建议

优先级建议：

1. 国内对象存储 / 制品库
2. 国内容器仓库
3. 私有 GitHub Release（不作为主方案）

---

## 10. GitHub Actions 结构建议

建议拆分为多个 workflow：

- `ci.yml`：代码校验、测试、构建
- `deploy-test.yml`：部署测试环境
- `deploy-prod.yml`：生产部署
- `miniapp-release.yml`：小程序上传与发布辅助

### 10.1 CI 流程

每次 PR 或 push 到开发分支时执行：

- 安装依赖
- lint
- test
- build
- 输出检查结果

### 10.2 测试部署流程

测试分支更新后：

- 构建产物
- 上传制品
- 自动部署测试环境

### 10.3 生产部署流程

主分支发布时：

- 先检查构建结果
- 再由负责人手动批准
- 再执行生产部署

### 10.4 关键原则

- 生产部署必须可审计
- 不允许测试环境配置直接进入生产
- 密钥与环境变量只保存在 GitHub Secrets 或云厂商密钥系统中

---

## 11. 国内网络优化建议

### 11.1 依赖源优化

建议使用国内镜像或加速：

- npm/pnpm 镜像源
- Docker 镜像加速
- Git clone 尽量使用可达性更高的网络环境

### 11.2 构建缓存

- Node 依赖缓存
- Docker layer 缓存
- 前端构建缓存

### 11.3 产物传输优化

- 使用对象存储
- 尽量避免跨境大文件直传
- 静态资源走 CDN

---

## 12. 安全与权限设计

### 12.1 Secrets 管理

以下内容不得硬编码：

- 数据库密码
- Redis 密码
- SSH 密钥
- 对象存储密钥
- 微信小程序密钥
- 发布平台 token

### 12.2 权限边界

- 只有少数发布角色可触发生产部署
- 小程序发布权限独立管理
- 测试环境自动部署权限与生产环境分开

### 12.3 审计要求

所有部署行为至少记录：

- 发起人
- 时间
- 分支/提交号
- 环境
- 部署结果
- 回滚结果

---

## 13. 回滚策略

### 13.1 前端回滚

- 保留最近一个稳定版本
- 出问题时切换 CDN 或对象存储版本

### 13.2 后端回滚

- 保留上一个可运行镜像
- 数据库兼容变更优先
- 不可逆迁移要单独审批

### 13.3 小程序回滚

- 通过微信平台回退到上一个稳定版本
- 重大版本上线前必须做充分测试

---

## 14. 数据库迁移策略

数据库迁移不应该隐藏在部署脚本里，而应该作为独立步骤：

1. 先备份
2. 再执行迁移脚本
3. 再部署应用
4. 再做健康检查

### 14.1 原则

- 迁移脚本必须可追踪
- 重要字段变更必须支持回退或补偿
- 线上大表变更要谨慎

---

## 15. 推荐实施路线

### 阶段 1：最小可用 CI/CD

- GitHub Actions 跑 lint / test / build
- 测试环境自动部署
- 生产环境人工发布
- 小程序手动审核发布

### 阶段 2：稳定化

- 制品库标准化
- 镜像仓库标准化
- 环境变量集中管理
- 部署日志审计化

### 阶段 3：平台化

- 引入国内 DevOps 平台
- 接入发布审批
- 接入监控与告警
- 接入回滚与灰度能力

---

## 16. 最终推荐落地模板

### 推荐组合

- GitHub：代码仓库
- GitHub Actions：CI 校验
- 国内对象存储：静态站点与制品
- 国内云服务器：后端与管理端部署
- 微信平台：小程序发布
- 人工审批：生产发布门禁

### 推荐理由

这套方式兼顾：

- 国内可用性
- 团队协作效率
- 商业项目的稳定性
- 后续架构演进空间

---

## 17. 结语

对于当前这个火锅食材 B2B 项目，CI/CD 最重要的不是“工具最潮”，而是“发布可控、部署稳定、国内能用、出了问题能回滚”。

因此建议先采用“GitHub Actions + 国内部署资源 + 人工审批”的方案起步，既不牺牲开发效率，也能保证真实商业项目的可落地性。
